# 앱과 본문 렌더러 CPU 사용률 비교

2026-10-09 아카라이브 플러스 0.9.32768의 순정 로직, 패치 0.3.6, 패치 0.3.7을 같은 Android 15 x86_64 에뮬레이터에서 비교했다. 화면은 1080×2280, 표시율 120Hz, 호스트 GPU, 가상 CPU 4코어다. 휴대폰 측정은 아니다.

## 무엇을 합산했는가

[Perfetto의 CPU 스케줄링 기록](https://perfetto.dev/docs/data-sources/cpu-scheduling)에서 실제 실행 중인 구간(`sched_slice`)을 앱의 모든 스레드와 그 앱에 연결된 WebView sandbox renderer 프로세스에 대해 합산했다. Android 서비스 연결 정보에서 renderer의 클라이언트가 `live.arca.android`임을 확인했다. 별도 스레드로 옮긴 작업도 합계에 들어간다. 앱 메서드의 벽시계 시간이나 UI 스레드 시간만 비교한 값이 아니다.

평균 CPU 사용률은 `합산 실행 시간 / 측정 구간 시간 / 4 × 100`이다. **가상 CPU 4코어 전체 용량을 100%**로 본 수치다. CPU 한 코어를 100%로 표시하는 도구의 수치는 이 표의 4배가 된다. 예를 들어 순정의 반복 전환 10.37%는 한 코어 기준 약 41.48%다.

SurfaceFlinger·그래픽 드라이버 서비스·GMS 등 다른 공유 OS 프로세스의 CPU와 호스트 PC의 CPU/GPU 사용률은 합계에 포함하지 않았다. 따라서 화면 표시로 인한 기기 전체 CPU 비용이나 전력 소모를 측정한 것은 아니다.

## 조건

- 순정 비교 APK는 재포장·같은 개인 키 서명만 했다. 원본의 `classes.dex`, `classes2.dex`, `classes3.dex`, `AndroidManifest.xml`이 바이트 단위로 동일함을 확인했다. 앱 계측 코드는 추가하지 않았다.
- 비교 APK마다 같은 `speed` 컴파일, 앱 재시작과 게시글 진입 3회 준비를 수행했다. 같은 앱 데이터·이미지 캐시를 사용했다. 최초 설치/엔진 초기화는 비교에서 제외했다.
- 같은 핫딜 게시글을 사용했다. 본문을 로드한 뒤 8초 정지 구간을 기록했다.
- 글과 목록을 4초 주기로 6번 왕복해 약 24초를 기록했다. 글에 2.8초 머문 뒤 뒤로 가고, 나머지 시간은 목록에서 기다렸다. 각 버전에서 두 번씩, 총 12회 왕복을 측정했다.
- 목록 정지 구간은 마지막 왕복 종료 후 6~14초의 고정 8초 구간이다. UI 도착 확인용 dump가 끝난 뒤를 사용했다.
- 순정 A → 0.3.7 A → 0.3.7 B → 순정 B → 0.3.6 A → 0.3.6 B 순서로 측정했다. 모든 추적에 기록 손실·오류 통계가 없었다. 녹화·빌드·다른 성능 추적은 동시에 실행하지 않았다.

## 결과

두 번의 합산 CPU 시간을 두 구간의 합산 경과 시간으로 나눈 평균이다.

| 동작 | 순정 로직 | 0.3.6 | 0.3.7 |
| --- | ---: | ---: | ---: |
| 글 진입·뒤로 가기 반복 | 10.37% | 8.76% | 8.82% |
| 글을 열어 둔 채 정지 | 0.815% | 0.806% | 0.819% |
| 목록에서 정지 | 0.015% | 0.020% | 0.018% |

| 반복 전환의 개별 측정 | 순정 로직 | 0.3.6 | 0.3.7 |
| --- | ---: | ---: | ---: |
| A | 10.238% | 8.641% | 8.696% |
| B | 10.503% | 8.881% | 8.941% |
| 두 번의 CPU 시간 합계 / 경과 시간 | 19.940s / 48.069s | 16.849s / 48.078s | 16.959s / 48.077s |

순정 대비 0.3.7은 이 반복 전환에서 **약 1.55%포인트, 상대적으로 약 15% 낮았다**. 이는 광고·추적 축소, 스프링·그리기 경로와 기존 본문 뷰 재사용 등을 모두 적용한 결과다. 이번 0.3.7 변경만의 효과로 해석하면 안 된다.

직전 0.3.6 대비 0.3.7은 8.76%에서 8.82%로, 약 0.06%포인트 높았다. 개별 측정 범위가 겹치고 두 번뿐이므로 추가 변경의 CPU 감소를 입증하지 못했다. HTML formatter 자체의 호출 수와 CPU 시간 감소는 [본문 처리 측정](article-rendering.md)에서 별도로 확인했으나, 앱 전체 작업에서는 작은 일부다.

반복 전환의 renderer CPU 합계는 순정 4.573s, 0.3.6 2.276s, 0.3.7 2.272s였다. 순정에서는 글 진입마다 renderer가 새로 생성됐고, 두 패치 버전은 한 renderer를 유지했다. 이 관찰은 기존 뷰 재사용이 주된 감소에 기여했음을 뒷받침한다. 다른 변경과 분리한 실험은 아니므로 기여율을 확정하지 않는다.

정지한 글과 목록에서는 뚜렷한 감소가 없었다. 0.3.7의 반복 전환 합산 CPU 시간 중 앱의 RenderThread는 약 54%를 차지했다. HTML 문자열 변환만 줄이는 것으로 모든 CPU 비용이나 끊김이 해결되지는 않는다.

## 한계와 유지보수

짧은 시나리오 두 번씩의 결과이며, 모든 채널·긴 글·동영상·다운로드·로그인·백그라운드 알림을 대표하지 않는다. 네트워크·호스트 부하·가상 GPU·Android 컴파일 방식과 캐시 상태가 결과에 영향을 준다. 실제 휴대폰 CPU 사용률 감소나 배터리 절감률로 환산하지 않는다.

본문 표시 최적화는 같은 포어그라운드 Activity에 빈 뷰와 renderer를 보관하므로 목록에서 메모리를 유지하는 비용이 있다. 앱을 벗어나거나 메모리가 부족하면 캐시 뷰를 해제한다. CPU 감소가 곧 모든 메모리 사용의 감소라는 뜻은 아니다.

재현 시 같은 앱·글·컴파일·옵션과 가상 CPU 개수를 기록하고, 앱뿐 아니라 renderer까지 합산해야 한다. `ts/dur`가 구간 경계를 넘으면 교집합 시간만 집계한다. 커널의 idle 스레드, 추적 도구와 공유 OS 서비스를 앱 CPU에 섞지 않는다. 원본 APK·개인 키·원시 추적은 저장소에 공개하지 않는다.
