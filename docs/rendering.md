# 슬라이드 그리기 개선과 유지보수

## 변경 범위

아카라이브 플러스 0.9.32768의 `Ka.n`에 있는 네 전환 함수 `g/i/k/m`을 수정한다. 들어오는 화면은 원래처럼 전체 너비만큼 오른쪽에서 이동하고, 나가는 화면은 너비의 30%만큼 왼쪽으로 이동한다. 뒤로 가기는 원래 방향을 유지한다. Activity 전환 리소스, 투명 창 테마, 이미지 렌더러는 변경하지 않는다.

스프링은 감쇠 비율 1.0, 강성 600, 위치 종료 기준 1px을 사용한다. 0.3.4의 강성 1200은 이동이 너무 급하게 느껴질 수 있어 되돌렸다. 강성이나 재생 시간을 바꾸는 것만으로 매 프레임의 처리 부담이 줄어드는 것은 아니다.

## 화면 배치 계산 줄이기

원본 `androidx.compose.animation.h.b(F0.M, F0.G, long)`은 슬라이드 상태 `V.H1.getValue()`를 측정 단계에서 읽고, 그 값을 배치 람다에 전달한다. 위치가 바뀔 때마다 측정 단계가 다시 무효화될 수 있다.

패치는 크기 애니메이션 `N`과 정렬 위치 애니메이션 `O`가 모두 없는 경우에만 이 읽기를 미룬다. 측정/배치에는 슬라이드 위치 0을 전달하고, 원래 그래픽 레이어 람다를 `local.arca.SlideLayer`로 감싸 실제 위치를 `translationX/Y`로 적용한다. 원본 람다를 먼저 실행하므로 기존의 투명도·크기 변환은 유지한다. 그래픽 레이어가 Compose 상태 읽기를 관찰하고 위치 변경 시 레이어 속성을 갱신한다. 크기나 정렬 애니메이션이 있는 경우 원본 측정 경로를 실행한다.

새 레이어, 타이머, 별도 애니메이터, 주사율 강제 설정을 추가하지 않는다. 정지한 화면에서 새 프레임을 계속 요청하지 않으며, 실제 배터리 감소량은 측정하지 않았다. 이 방식은 [Compose의 애니메이션 성능 가이드](https://developer.android.com/develop/ui/compose/animation/quick-guide#optimize-animation-performance)와 [그래픽 레이어 설명](https://developer.android.com/develop/ui/compose/graphics/draw/modifiers#graphicslayer)을 참고했다.

## 앱 업데이트 시 확인

`compile-stubs`에는 빌드용으로 직접 작성한 최소 API 선언만 있다. `compileOnly` 의존성이므로 대상 APK에 포함하지 않는다. 실제 구현은 대상 앱의 Compose 클래스를 사용한다. 원본 앱 소스나 APK는 저장소에 포함하지 않는다.

업데이트된 APK에서는 다음을 다시 확인한다.

1. `Ka.n`의 네 메서드, 원래 tween 호출, 레지스터 수와 이동 방향 함수가 여전히 일치하는지 확인한다.
2. 측정 메서드에서 `P`가 슬라이드 상태인지, `N/O`가 크기/정렬 애니메이션인지 확인한다. 주입 시 사용하는 v0/v1/v3/v12 레지스터 배치도 확인한다.
3. `V.H1`, `c8.l`, `b1.p`의 API와 IntOffset의 좌표 포장을 확인한다. 현재 X는 상위 32비트, Y는 하위 32비트다.
4. 그래픽 인터페이스의 `D/A`가 translationX/Y getter, `l/h`가 setter인지 확인한다. 패치는 구현 클래스의 연결 필드까지 검사하며, 이름만 같고 의미가 바뀐 경우를 경계한다.
5. 앞으로 이동·뒤로 이동·전환 중 빠른 뒤로 가기·터치 좌표·스크롤·가로 회전·글과 댓글 로딩을 확인한다. 크기 변화가 있는 다른 전환은 원본 경로가 유지되는지도 확인한다.

현재 앵커나 검사 조건이 달라지면 패치 적용을 중단한다. 새 버전의 의미를 확인하지 않은 채 검사만 느슨하게 하지 않는다. 버전 제한이 없는 대상도 실험용이며 향후 모든 버전의 호환성을 보장하지 않는다.

## 120Hz 검증의 한계

120Hz에서는 갱신 간격이 약 8.33ms다. 테스트 AVD의 표시 모드와 앱의 프레임 간격을 모두 확인했다. 에뮬레이터는 호스트 GPU·부하의 영향을 받고, 화면 녹화와 상세 추적 자체도 성능에 영향을 준다. 성능 비교에서는 녹화·atrace를 끄고 동일한 스프링, 동일한 앱 컴파일 방식, 동일한 설정 화면 경로를 사용했다. 각 이동 후 UI를 읽어 의도한 화면에 도착했는지 확인했다. 실제 휴대폰을 연결한 검증은 사용자 요청대로 생략했다.

동일한 강성 600/종료 기준 1px으로 설정→다운로드 큐→뒤로 가기를 6회 반복한 짧은 측정에서는, 원본 측정 경로가 883프레임 중 지연 21회(2.38%), 레이어 경로가 881프레임 중 24회(2.72%)였다. 차이가 작고 측정 노이즈가 있으므로 프레임 지연 감소를 입증하지 못했다. 특히 단순한 설정 화면의 결과를 무거운 게시글이나 실제 휴대폰의 결과로 일반화할 수 없다. 코드상 슬라이드 상태의 측정 단계 의존성은 제거했지만, 이 변경만으로 모든 버벅임이 해결되었다고 주장하지 않는다.
