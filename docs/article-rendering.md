# 본문 표시 최적화와 유지보수

## 문제와 변경 범위

플러스 0.9.32768은 글 본문을 `Da.c` WebView로 표시한다. `A9.g.i`가 뷰를 새로 만들고 설정·콜백을 붙이며, 화면을 나가면 `Da.c.onDetachedFromWindow`에서 `Da.d.a`를 통해 파괴한다. 다음 글에서 이 생성·설정 비용이 다시 UI 스레드에 발생한다. WebView 엔진의 최초 초기화는 이보다 훨씬 큰 별도 비용이다.

0.3.6은 같은 Activity와 정확히 같은 Context에서 본문 뷰 한 개를 재사용한다. `local.arca.BodyWebViewCache`에는 일시정지한 뷰 하나만 보관한다. 화면을 닫을 때 원래 생명주기 도우미로 먼저 일시정지하고 활성 뷰 집합에서 제거한 뒤, 이전 글의 리스너 `D`와 HTML 비교용 캐시 `E`를 지운다. 다운로드·WebView·Chrome·자바스크립트 콜백을 해제하고 로딩을 멈춘 다음 `about:blank`를 표시한다. 다음 글에서는 원래 팩토리가 새 설정과 리스너를 붙이고 새 HTML을 전달한다. 쿠키와 공유 HTTP 캐시는 지우지 않는다.

새 창이나 백그라운드 페이지를 미리 만들지 않는다. 글을 미리 내려받지 않는다. 앱의 Activity가 일시정지되거나 파괴될 때, 설정·기기 구성 변경과 메모리 부족 때 보관한 뷰를 파괴한다. 부모가 남아 있거나 Context가 다르면 재사용하지 않는다. 캐시된 뷰의 렌더러가 종료된 경우에도 뷰를 버린다. 활성 본문의 원래 렌더러 오류 처리는 유지한다. 메모리 한 개의 뷰를 보관하는 비용은 있으며, 모든 메모리 사용이 줄어드는 방식이라고 주장하지 않는다.

`Da.d.c`에서는 기존 활성 뷰 집합에 이미 들어 있는 뷰의 중복 `onResume`을 생략한다. 첫 재개, 모든 일시정지, 전역 타이머 정지·재개와 CAPTCHA 뷰의 원래 종료 경로는 유지한다.

## 화면 전환과 본문 로딩 분리

`Ea.d.observeResumeAsState`에서 관찰하는 원래 생명주기 상태가 본문 갱신 함수 `Da.c.f(html, resumed)`로 전달된다. Navigation의 새 화면은 전환 중에는 아직 RESUMED가 아니다. 옵션을 켠 경우 이 상태가 false이면 뷰를 일시정지하고 HTML 로딩을 시작하지 않는다. 원래 상태가 true로 갱신되면 최신 HTML을 로딩한다. 정해진 밀리초 대기, 타이머, 별도 프레임 루프는 추가하지 않는다. API의 글·댓글 가져오기나 원래 스프링 이동 방향·거리는 변경하지 않는다.

뷰 재사용만 적용한 시험에서는 본문 준비가 빨라져 이미지 그리기가 이동과 겹치는 GPU 지연이 남았다. 생명주기 상태에 맞춰 로딩한 최종 구현에서 이 겹침을 줄였다. 이미지 자체의 디코딩·업로드와 매우 무거운 HTML의 비용을 없앤 것은 아니다. 최초 WebView 엔진 초기화도 남는다.

**설정 → Morphe 설정 → 본문 표시 최적화**에서 켜고 끌 수 있다. 기본값은 켜짐이며 앱을 다시 실행해도 유지한다. 끄면 다음 글부터 매번 뷰를 파괴하고 새로 만드는 방식과 원래 HTML 준비·로딩 시점으로 돌아간다. 설정값은 메모리에 캐시하므로 매 뷰 갱신마다 설정 파일을 읽지 않는다.

## 0.3.7의 CPU 중복 작업 제거

원본 `Ya.n.j(String, List, boolean)`의 마지막 HTML 선택은 `Ka.g.a(condition, button + html, html)` 형태다. 함수에 넘기는 인자를 먼저 계산하므로 같은 DOM을 `Ya.o.a(Nb.f)`로 두 번 문자열로 만들고, 버튼을 표시하지 않을 때도 `Ya.n.i(boolean)`과 문자열 결합을 실행한다. 패치는 HTML 문자열 하나를 재사용하고 원래 조건이 참일 때만 원래 버튼 함수를 호출한다. 테마·원래 이미지 접기 조건·iframe 감싸기·투표 변환·이미지 목록 생성은 유지한다. 이 중복 계산 제거는 옵션과 관계없이 적용된다.

본문 표시 최적화를 켜면 서버 응답 이전의 빈 HTML과 빈 투표 목록은 DOM 준비를 생략한다. 실제 본문 준비는 `PreparedBody`가 원래 remember 키(본문·투표·테마)를 유지하며 실행한다. Compose의 `RememberObserver`가 기억한 작업만 시작하므로 버려진 임시 composition에는 일을 만들지 않는다. 백그라운드 우선순위의 작업자 한 개가 유한한 원래 formatter를 호출하고 완료 결과를 UI 스레드의 Compose 상태로 전달한다. 화면을 나가면 작업을 취소하고 대기열에서 제거한다. 이미 실행 중인 원래 파서는 중단 요청을 즉시 처리하지 않을 수 있으나 결과는 폐기한다. 작업자가 10초 동안 쉬면 종료한다. 스레드 이동 자체가 전체 CPU 계산량을 줄인다고 주장하지 않는다.

`BodyGate`는 첫 본문 뷰 생성도 원래 resumed-state가 참이 된 뒤에 시작한다. 한번 표시한 본문은 화면을 나갈 때 상태가 false가 되더라도 유지해 퇴장 전환 중에 사라지지 않는다. 정해진 대기 시간이나 새 생명주기는 추가하지 않는다. 옵션을 끄면 동기 HTML 준비와 원래 뷰 생성 시점으로 돌아간다. 빈 본문을 생략한 결과는 내용이 오면 원래 remember 키가 바뀌어 교체된다.

2026-10-09 같은 120Hz 에뮬레이터에서 같은 게시글을 4번씩 열고 첫 진입을 제외했다. 비교용 순정은 서명·재포장과 로컬 계측만 추가했고 앱 로직은 유지했다. 양쪽 모두 같은 `speed` 컴파일을 적용했다. HTML formatter에만 `Debug.threadCpuTimeNanos()`를 사용했다.

| 측정 범위 | 순정 로직 | 0.3.7 후보 |
| --- | --- | --- |
| 글 한 번 열 때 formatter 호출 | 빈 본문 + 실제 본문, 2회 | 실제 본문만, 1회 |
| 각 formatter 안의 최종 DOM 문자열 생성 | 2회 | 1회 |
| 글 진입당 formatter CPU 시간 합계, 반복 3회 | 1.44 / 1.34 / 1.70ms | 0.94 / 0.85 / 1.11ms |
| 실제 본문만의 formatter CPU 시간 | 0.82 / 0.84 / 0.87ms | 0.94 / 0.85 / 1.11ms |
| 진입마다 가장 긴 프레임 | 92.1 / 91.7 / 92.6ms | 46.9 / 74.8 / 155.7ms |
| 뒤로 가기마다 가장 긴 프레임 | 21.5 / 25.0 / 25.4ms | 17.3 / 17.7 / 17.7ms |

호출과 문자열 생성 횟수 감소는 계측으로 확인했다. 이 짧은 테스트에서는 빈 본문 생략으로 formatter 합계가 줄었지만, 실제 본문 하나의 CPU 시간은 일관되게 줄지 않았다. Future·Compose 상태 처리나 앱 전체 CPU 시간은 위 표에 포함하지 않았다. 이후 앱과 renderer를 합산한 [CPU 사용률 비교](cpu-comparison.md)에서 순정 대비 약 15% 낮았으나, 직전 0.3.6 대비 추가 감소는 입증하지 못했다. 후보의 긴 프레임도 남아 있으므로 평균적인 부드러움 향상을 입증하지 못했다. 첫 실행의 클래스·WebView 초기화와 이미지 디코딩·렌더링 비용도 남는다. 실제 휴대폰 CPU 사용률·120Hz 부드러움·배터리 절감률은 측정하지 않았다.

고정 입력 5개(빈 글, 한글/엔티티, 표/링크, 접을 수 있는 이미지, iframe/동영상)를 밝고 어두운 테마와 데이터 절약 끄기/켜기에 적용한 20개 출력은 순정과 길이·해시가 모두 같았다. 버튼이 생기는 접힌 이미지 조건도 포함했다. 진단 클래스와 계측 패치, 테스트 APK는 공개하지 않는다.

최종 0.3.7 번들을 원본 Plus에 적용해 세 기본 패치·재빌드·서명이 모두 성공했다. 배포 APK에서 서로 다른 두 글의 본문과 댓글 표시, 이미지 확대 화면, 홈에 나갔다 복귀, 본문 옵션 끄기 후 재실행과 글 표시, 옵션 다시 켜기를 확인했다. Morphe 설정의 첫 옵션과 스위치가 화면 안에 표시된다. 크래시 로그와 제거한 진단 로그는 없었다. 로그인·글/댓글 전송과 실제 기기 검증은 이번 작업에서 수행하지 않았다.

## 측정과 확인

아래는 0.3.6에서 뷰 재사용 옵션을 비교한 이전 측정이다.

Android 15 x86_64 AVD, 호스트 GPU, Android 표시율 120Hz, 실제 프레임 간격 8,333,333ns에서 같은 핫딜 게시글을 반복해서 열고 닫았다. 각 테스트 APK에 같은 `speed` 컴파일을 적용했고, 녹화와 atrace는 껐다. 측정 후 UI를 읽어 목록과 본문 도착을 확인했다. 각 모드의 첫 진입은 아래 비교에서 제외하고 이후 세 번만 비교했다.

| 관찰 구간 | 옵션 꺼짐 | 최종 옵션 켜짐 |
| --- | --- | --- |
| 본문 팩토리 준비 | 9.6 / 15.3 / 12.1ms | 0.6 / 1.4 / 0.6ms |
| HTML 갱신 호출 | 5.1 / 3.1 / 4.0ms | 1.1 / 1.3 / 1.6ms |
| 진입마다 가장 긴 프레임 | 50.7 / 58.1 / 49.0ms | 33.8 / 42.4 / 41.0ms |
| 뒤로 가기마다 가장 긴 프레임 | 17.1 / 16.6 / 16.3ms | 18.1 / 17.7 / 18.2ms |

별도의 진단 빌드에서 시간을 기록했다. 공개 번들에는 진단 클래스·로그·진단용 패치를 넣지 않는다. 에뮬레이터의 CPU/GPU와 네트워크 상태는 변동한다. 이 짧은 비교는 특정 구간의 비용 감소를 보여주지만, 실제 휴대폰의 120Hz 부드러움이나 배터리 절감량을 입증하지 않는다. 처음 엔진을 사용하는 진입은 약 147–211ms의 팩토리 비용이 관찰됐고 여전히 남는다.

서로 다른 글의 본문 교체, 이미지 확대와 복귀, 댓글 화면, 옵션 끄기와 앱 재시작 후 유지, 앱 밖으로 나갔다 복귀, 메모리 부족 신호와 빠른 뒤로 가기를 확인했다. 계정 로그인과 글·댓글 전송은 이번 검증 범위에 포함하지 않았다.

## 앱 업데이트 후 확인

패치 시 다음 조건을 확인하며 달라지면 적용을 중단한다.

1. `A9.g.i`의 본문 뷰 생성·설정 순서, Context와 뷰 레지스터, 생성자와 리스너 API.
2. `Da.c.D/E`의 타입, HTML 캐시 읽기와 `loadDataWithBaseURL`, `webViewTunnel` 자바스크립트 인터페이스 이름.
3. `Da.c.onDetachedFromWindow`의 원래 종료 호출과 레지스터.
4. `Da.d.c`의 활성 집합과 최초 재개·전역 타이머 처리.
5. `Ea.d`의 resumed-state 관찰과 `u9.t`의 본문 화면이 그 상태를 사용하는지.
6. `u9.t.l`의 HTML remember 그룹과 formatter 호출 레지스터, `V.Z0`의 기억/폐기 콜백, `V.w1/w0`의 상태 API.
7. `Ya.n.j`의 최종 HTML 선택 구간, `Ya.o.a`의 DOM 문자열 생성 의미와 원래 버튼 조건. 이름만 같은 다른 변환을 한 번 호출하도록 바꾸면 안 된다.
8. `A9.g.g`의 본문 restart 그룹과 종료 콜백, 첫 진입/퇴장 시 resumed-state의 의미.

새 버전에서는 상태 의미까지 다시 확인한다. 같은 이름의 boolean이라고만 보고 로딩을 미루면 안 된다. 글 전환·뒤로 가기·이미지/동영상·다운로드·댓글·배경 복귀·회전·글꼴/테마 변경·저메모리 상태를 확인하고, 이전 글의 내용이나 콜백이 다음 글에 남지 않는지 확인한다. 순정 앱의 구버전이나 미래 버전을 자동으로 지원한다고 보장하지 않는다.
